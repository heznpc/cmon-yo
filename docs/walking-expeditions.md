## 확정한 사용자 시나리오

1. **혼자 걷기:** iOS 걷기 탭에서 건강 기록 읽기를 요청합니다. 현재 걸음 수와 최근 동기화 상태를 보고, 원정·보상 화면에서 1,000보마다 1P를 받습니다. 하루 인정 상한은 10,000보입니다. 3,000보에서 3P를 받은 후 5,000보가 되면 추가 2P만 받을 수 있습니다.
2. **원정 만들기:** 이름과 선택적인 공원을 정해 초대 코드를 만듭니다. 원정은 서울 시간 기준 다음 날 00:00에 시작해 7일 동안 진행됩니다. 시작 전 최대 5명까지 참가하며 참가자의 표시 이름·원정 기여가 동료에게 공유됩니다. 한 계정은 겹치는 모집/진행 원정 하나에 참가합니다.
3. **함께 단계 열기:** 개인의 일별 인정 걸음이 원정에 반영됩니다. 10,000보·30,000보·60,000보에서 세 단계가 열립니다. 각자 1,000보 이상 기여한 동료가 2명 이상 있어야 단계 보상을 받습니다. 본인도 1,000보 이상 기여해야 하며, 단계별 5P·10P·20P를 계정마다 한 번 받습니다. 순위 경쟁 대신 공동 진행과 각자의 기여를 표시합니다.
4. **보상 사용:** 포인트로 새싹 산책가(5P), 동네 탐험가(20P), 원정 동료(50P) 배지를 교환합니다. 같은 배지는 중복 구매하지 않으며 잔액 차감과 배지 소유권은 한 트랜잭션으로 저장합니다.
5. **동네로 연결:** 선택한 시설의 상세와 공개 커뮤니티 작성 화면으로 이어집니다. 시설을 지정했다는 사실이나 걸음 기록으로 장소 방문을 인증하지 않습니다. 공개 글 작성에 자동 포인트를 지급하지 않습니다.

원정은 이번 기간의 파티입니다. 기존 약속인 `meetups`, 현장 확인인 `attendance`, 지속 동호회 모델과 합치지 않습니다. 게임의 단계는 가상 진행이며 실제 이동 경로나 장소 도착을 뜻하지 않습니다.

외부 현금·기프티콘의 교환권·지급 재원·공급자 연결은 현재 구현하지 않습니다. 앱 내부 포인트와 배지는 외부 교환 가치를 약속하지 않습니다. 실제 교환을 붙일 때는 공급자 주문·잔액 예약·실패 복구·정산 모델을 추가합니다.

## 기록과 게임 진행의 규칙

- Native는 HealthKit의 날짜별 합계를 읽습니다. 개별 원본 건강 샘플·이동 경로를 웹뷰 메시지나 서버 로그에 싣지 않습니다.
- 데이터가 없거나 읽을 수 없는 경우를 0보 또는 권한 거부로 확정하지 않습니다. HealthKit 권한 요청의 성공은 읽기 허용의 증거가 아닙니다.
- 서비스 회차는 `Asia/Seoul` 기준입니다. 기기 시간대가 바뀌어도 같은 날의 보상을 다시 생성하지 않습니다.
- Native 요청은 서버 인증을 거칩니다. 서버는 오늘과 최근 7일의 집계만 수락하고, 일별 현재 값과 게임에 반영한 최대값을 분리합니다. 오래된 revision은 새로운 기록을 덮어쓰지 못하고, 같은 revision의 다른 내용은 충돌입니다.
- 현재 건강 기록이 줄어도 인정한 게임 진행·받은 포인트는 소급 차감하지 않습니다. 추가 진행은 기존 인정 최대값을 넘어섰을 때만 발생합니다. 이 규칙은 반응이 안정적인 게임 보상을 위한 선택이며 건강 기록의 정확성이나 외부 교환용 부정방지 보장이 아닙니다.
- 한 계정의 활성 동기화 출처를 명시합니다. 기기를 바꾸어도 같은 날짜를 더해 적립하지 않습니다. Native 계정 변경은 대기 중 요청과 건강 동기화 기록의 소유 경계입니다.
- 참가가 닫힌 원정에는 중간 참가하지 않습니다. 시작 전에는 나갔다가 모집 기간 안에 다시 참가할 수 있습니다. 시작 후 나간 사람은 새 기여·남은 보상을 받을 수 없으며 같은 원정에 재가입하지 않습니다. 이미 반영한 공동 진행은 보존합니다.
- 늦게 도착한 기록은 허용된 날짜 범위에서 원정 기간에 속한 날짜에만 반영합니다. 원정 보상 수령은 종료일로부터 7일 이내입니다.
- 계정 삭제 시 개인 건강 집계·자격증명·개인 포인트 기록은 제거하고 공동 진행에 필요한 익명 기여 스냅샷은 남깁니다.

HealthKit의 변경·삭제와 날짜별 재집계는 [Apple 동기화 설명](https://developer.apple.com/videos/play/wwdc2020/10184/)을 참고했습니다. [읽기 권한의 비공개성](https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data)과 [백그라운드 전달 제한](https://developer.apple.com/documentation/healthkit/hkhealthstore/enablebackgrounddelivery(for:frequency:withcompletion:))을 UI 상태와 구현 한계에 반영합니다. 현재 잠금 중 항상 전송되거나 매 걸음 실시간으로 서버에 반영된다고 보장하지 않습니다.

## 코드와 이행 경계

- `src/contracts/walking.ts`: 화면·Native·HTTP가 공유하는 정책, 명령, 응답 스키마.
- `src/server/walking/`: 실제 집계, 원정, 보상 원장과 트랜잭션.
- `src/server/walking-routes.ts`: 인증·계정·origin 경계, API와 같은 service를 호출하는 SSR.
- `src/features/quests/`: React 원정·개인 보상·배지 화면. `/quests`로 접근합니다.
- `ios/CmonYo/Walking/`: 기기 건강 기록과 동기화. 인증된 WebView에서 `/quests?surface=native`를 엽니다.
- `src/api/http.ts`, `src/contracts/command.ts`: 기존 모임·커뮤니티 전용 이름에 묶였던 공통 HTTP·명령 결과 계약.
- `db/006_activity_quests.sql`: 새로운 걷기·원정·리워드 도메인. 이전 미커밋 팀 퀘스트 초안을 이 시나리오로 대체합니다.

기존 SQL001–005는 보존합니다. `schema_migrations`는 적용 파일과 체크섬을 기록합니다. 기존 idempotent SQL은 기존 migration 호출의 반복 적용 의미를 유지하고, 새006은 기록이 있을 때 다시 실행하지 않습니다. `migrateMeetings`는005까지만 다루며 원정 스키마를 자동으로 생성하지 않습니다. Auth migration은 Better Auth의 계획을 먼저 확인합니다. 기존 파일 체크섬이 바뀌면 중단하고 새로운 migration으로 변경해야 합니다.

배포 코드는 기존과 같은 모노레포·단일 Fastify SSR/API·PostgreSQL입니다. npm workspace·별도 서버·범용 퀘스트 엔진을 선행 도입하지 않습니다.

Native의 기본 탭은 걷기입니다. 원정 WebView는 `/quests`를 소유하며, 시설·공개 후기 링크는 브라우저에서 열도록 안내합니다. 이때 브라우저 로그인은 별도로 필요할 수 있습니다. React 링크도 이 경계를 따라 새 탐색을 요청하며 Native 토큰을 JavaScript로 전달하지 않습니다. 기존 모임의 댓글 WebView 흐름은 별도로 유지합니다.

명령 성공 건수는 DB에서 계정별로 제한합니다. 실패한 초대 코드 입력 등은 별도로 프로세스당 계정별 분당 60회로 제한하며 메모리 항목 수도 제한합니다. 서버를 여러 대로 늘리면 실패 시도 제한도 공용 저장소나 게이트웨이로 옮겨야 합니다.

## 다음 실행 가능 시 수행할 명령 — 이번 작업에서는 실행하지 않음

```sh
npm run with-env -- migrate
npm run with-env -- check
npm run with-env -- test:web -- --project=meetings-development --project=meetings-production
```

새 migration은 먼저 별도 시험 DB에 적용하고 재적용·기존 데이터 보존을 확인해야 합니다. 공유 개발 DB나 운영 DB에 실행한 기록은 없습니다. 첫 실행 시 건강 권한·HealthKit 응답·WebView 세션·작은 화면·앱 복귀는 별도 확인해야 합니다.
